# Persona C：潜在员工 / 贡献者（T3）

> 目标：让内容既能吸引“想加入的人”，也能筛选“适合这种协作方式的人”。

## C 层定义

C 层受众是“愿意作为员工、自由贡献者或项目合作者，参与 AI-native 组织实践的人”。

## 共性画像（C 层）

- 典型职位（映射，不作为分层依据）：工程师、产品经理、运营负责人、设计师、增长负责人、独立开发者
- 典型组织规模：个人到 2000 人组织（重点是角色心智，不是公司体量）
- 职责镜头（按需求分组）：
  1. 评估个人能力是否能放大的人（多见于 IC）
  2. 评估是否有明确目标和结果责任的人（多见于 DRI）
  3. 评估团队是否支持成长与协同的人（多见于 PC）
- 日常阅读的 3 个平台（细化到账号/栏目/内容）：
  1. 微信公众号：
     - 常看：技术实践、产品方法、组织管理类公众号
     - 常读内容：实战复盘、工具链、职业成长路径
  2. 小红书：
     - 常看：AI 工作流实操号、效率工具号、职场发展号
     - 常读内容：岗位转型经验、技能图谱、作品案例
  3. 抖音：
     - 常看：编程实战类、产品拆解类、管理认知类账号
     - 常读内容：短平快教程、失败经验、认知升级
- 最关注的 5 个话题：
  1. 在 AI-native 团队里，个人能力如何被放大（IC）
  2. 如何把“会用工具”升级为“能交付结果”（DRI）
  3. 角色边界如何定义，协作冲突如何处理（PC）
  4. 如何建立可迁移的作品与方法资产（IC/DRI）
  5. 团队是否重视成长、反馈与复盘机制（PC）
- 典型痛点 3 条：
  1. IC 维度：会工具但缺少系统化交付方法，成果不稳定
  2. DRI 维度：任务很多但目标不清，难形成可验证结果
  3. PC 维度：跨职能协作低效，反馈回路慢，成长成本高
- 典型反对意见 2 条：
  1. “AI 会不会只是加班放大器，而不是能力放大器？”（IC/DRI）
  2. “组织强调速度，会不会牺牲培养和长期成长？”（PC）
- 判断内容“值不值得看完”的 3 个信号：
  1. 是否给出从学习到交付的具体路径（IC/DRI）
  2. 是否有真实角色案例而非空泛鸡汤（IC）
  3. 是否明确团队协作机制和反馈周期（PC）

## 画像样本 01

### C1｜3-5 年经验工程师（想从执行者升级为 DRI）

- 典型职位：后端/全栈工程师
- 典型组织规模：200 人互联网公司
- 日常阅读的 3 个平台：微信公众号（技术架构）、小红书（效率实操）、抖音（工程实践短视频）
- 最关注的 5 个话题：
  1. 如何从“接需求”变成“定义问题 + 拿结果”（DRI）
  2. AI 编码工具如何融入工程规范（IC）
  3. 如何减少返工并提升交付确定性（DRI）
  4. 如何建设个人方法库与模板库（IC）
  5. 如何与产品/运营高效协作（PC）
- 典型痛点 3 条：
  1. 需求变化快，缺少稳定拆题框架（DRI）
  2. 工具很多但评估标准混乱（IC）
  3. 沟通成本高，问题暴露太晚（PC）
- 典型反对意见 2 条：
  1. “这些方法会不会只适合管理层，不适合一线工程师？”（IC）
  2. “强调流程会不会降低开发速度？”（DRI）
- 判断内容“值不值得看完”的 3 个信号：
  1. 是否附带可执行模板（DRI）
  2. 是否有工程指标前后对比（IC/DRI）
  3. 是否给出跨团队协作示例（PC）

## 画像样本 02

### C2｜内容运营/产品运营（希望转型 AI-native 贡献者）

- 典型职位：内容运营、增长运营、产品运营
- 典型组织规模：80 人创业公司
- 日常阅读的 3 个平台：小红书（运营案例）、微信公众号（方法论）、抖音（工具演示）
- 最关注的 5 个话题：
  1. 如何用 AI 降低重复劳动并提升产能（IC）
  2. 如何定义与证明内容/增长 ROI（DRI）
  3. 如何与技术同学形成稳定协作（PC）
  4. 如何从“执行任务”升级为“负责结果”（DRI）
  5. 如何建立可复用 SOP 与复盘机制（PC）
- 典型痛点 3 条：
  1. 工具散、流程散、数据散，复盘困难（IC）
  2. 目标口径不一致，价值难讲清（DRI）
  3. 协作链路长，反馈闭环慢（PC）
- 典型反对意见 2 条：
  1. “如果没有技术背景，AI-native 是不是很难参与？”（IC）
  2. “这些方法会不会增加流程负担？”（PC）
- 判断内容“值不值得看完”的 3 个信号：
  1. 是否有低门槛可执行步骤（IC）
  2. 是否有可量化成果样例（DRI）
  3. 是否明确跨职能协作接口（PC）

## 画像样本 03

### C3｜独立开发者 / 社区贡献者（外部协作型）

- 典型职位：独立开发者、开源贡献者、技术写作者
- 典型组织规模：个人或 2-10 人小团队
- 日常阅读的 3 个平台：X（前沿动态）、GitHub（项目协作）、微信公众号（中文复盘）
- 最关注的 5 个话题：
  1. 如何在有限时间内做出高质量可展示成果（IC）
  2. 如何与团队建立清晰协作边界（DRI/PC）
  3. 如何提升作品可复用性与影响力（IC）
  4. 如何把一次协作沉淀为长期关系（PC）
  5. 如何避免被“临时需求”牵着走（DRI）
- 典型痛点 3 条：
  1. 需求输入模糊，交付边界频繁变动（DRI）
  2. 项目上下文不足，返工高（IC）
  3. 缺少固定反馈节奏，协作体验不稳定（PC）
- 典型反对意见 2 条：
  1. “如果不能沉淀作品与方法，这类合作价值有限。”（IC）
  2. “如果沟通成本高于开发成本，就不值得参与。”（PC）
- 判断内容“值不值得看完”的 3 个信号：
  1. 是否提供明确协作协议和验收标准（DRI）
  2. 是否给出可公开复用的资产模板（IC）
  3. 是否有长期协作机制说明（PC）
