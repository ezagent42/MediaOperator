# 提案 01：运营方案 v1 结构重排与 v0 归档

> 状态：Draft，供 PR 内讨论。合并前不会改动 `docs/notes/2026-04-23-init-plan.md`。

## 1. 背景

现稿 `docs/notes/2026-04-23-init-plan.md` 是第一版运营方案（下称 v0），已经搭起"渠道—矩阵—生产—自动化"的骨架，但叙述序是从"系统能力"出发，不是从"运营目标"出发。

外部评审意见（`improve_suggestion.md`）指出 8 个问题，其中 5 个是结构性的，3 个是表述层的。结构性问题必须靠重排章节来解决，表述层问题可以在后续 PR 中逐段改写。

**本 PR 的目的只有一个**：就"新版大纲长什么样"和"v0 怎么归档"达成一致。真正的内容改写放到后续实施 PR。

## 2. 提议

### 2.1 新版大纲（v1）

共 7 正文章 + 1 附录章，顺序严格如下：

1. 项目背景与阶段目标
2. 目标受众与核心信息
3. 渠道策略与主阵地选择
4. 内容矩阵与固定栏目
5. 周产能与内容生产流程
6. 内部协同机制与角色分工
7. 指标体系与复盘机制
8. 附录（监控库执行表格、周排期模板、术语表、工具层能力映射）

设计原则：

- **前 7 章全部是"人和业务的决策"**，不出现具体工具名。
- **第 8 章附录集中所有可替换件**（种子资源、工具链、模板），日后替换工具不影响正文。
- 主文件保持单一 markdown，附录如果超过 400 行再拆分到独立文件。

### 2.2 v0 归档策略（候选方案）

| 方案 | 做法 | 好处 | 代价 |
|---|---|---|---|
| A. 直接覆盖 | v1 直接替换 v0 内容；依赖 git 历史回溯 | 仓库最干净 | 非技术同事看历史不直观 |
| B. 归档重命名 | v0 重命名为 `docs/notes/archive/2026-04-23-init-plan-v0.md`，新增 `docs/notes/2026-04-23-plan-v1.md` | 文件直观并列，复盘方便 | 多一个目录 |
| C. 单文件版本头 | 保留原文件名，顶部写版本表、v0 内容折叠到文末 `<details>` 里 | 单文件，无需跳转 | 文件膨胀，v2 时更乱 |

**推荐 B**。理由：这是第一阶段产物，未来几个月还会有 v2/v3，早点建立 `archive/` 目录比单文件堆叠更可扩展。

### 2.3 配套目录结构

合并后的 `docs/notes/` 应该长这样：

```
docs/notes/
├── 2026-04-23-plan-v1.md              # 新版主文件
├── archive/
│   └── 2026-04-23-init-plan-v0.md     # 归档
└── proposals/                          # 提案文档（讨论完可留可删）
    ├── 01-plan-v1-structure.md        # 本文件
    ├── 02-phase1-positioning.md
    ├── 03-monitoring-library.md
    └── 04-vendor-integration.md
```

附录如果要独立拆文件，放在 `docs/notes/appendix/` 下。

## 3. 讨论点（留给 mentor 与 intern 在评论区拍板）

1. **v0 归档方案选 A/B/C？** 推荐 B，但如果 intern 觉得 A 足够、git 历史用起来顺手，也可以。
2. **8 章顺序是否合理？** 尤其是"渠道策略"放在"目标受众"之后，还是先讲渠道再讲受众？—— 提案是"先受众，再渠道"（先知道给谁看，才好选哪发）。
3. **附录是否一开始就拆文件？** 提案是"超 400 行再拆"。intern 可以根据实际写起来的体量决定。
4. **`docs/notes/proposals/` 目录的命运**：讨论结束合并后，这些提案文档是删除、保留还是移到 `archive/proposals/`？—— 提案是"保留在原位，作为决策痕迹"。
5. **命名约定**：`2026-04-23-plan-v1.md` 用建仓日期还是 v1 起草日期？—— 提案是"保持建仓日期不变，版本号区分迭代"。
