## 二、字段语义层（T1 初审重点）

任务清单原话："字段结构最重要，第一版对了后面 3 份就省力。"以下是 mentor 视角下 T1 阶段必须锁死的字段语义与结构原则——M1 是字段语义层、M2 是共性画像 scope 切分层、M3 是条目角色标注层。三者属于不同抽象层，互不替代。任何一条不立标尺，T2 / T3 / T4 都会复制同一种模糊。

### 2.1 「日常阅读的 3 个平台」语义未定义（M1，阻塞）

**观察。** 共性画像、A1、A2 三处的"3 个平台"完全一致：微信公众号、小红书、抖音。这恰好等于 mentor 在背景里拍板的"主阵地"。

**问题。** 这个字段的语义是哪一个？
- 解释 A：描述该群体的真实媒介行为（信息消费习惯）
- 解释 B：声明我方打算用哪三个阵地触达他

两种解释都合法，但**指向完全不同的下游使用方式**：
- 若是 A，T2 partner / T3 talent 的"日常阅读"应当独立调研，可能与 A 层差异巨大
- 若是 B，T2 / T3 / T4 直接照抄主阵地即可——但这样此字段不再是"画像字段"而是"渠道字段"

**附加质疑。** 一个 300 人 ToB SaaS 的 COO（A1）真的会把小红书放进 top 3 职业信息源？同类角色更常见的实际信息源更可能包括 LinkedIn 中文区 / 即刻 / 知乎专栏 / 行业播客 / 36氪。如果按解释 A 写，证据偏弱；如果按解释 B 写，应当在文档头部明示语义。

**建议。** 在 persona-a-client.md 顶部加 1 行字段语义注释，二选一并锁定；T1 锁定后写入 task-02 顶部作为 T2/T3/T4 共同字段约定。

### 2.2 共性画像 scope 切分维度错位 — 按职位列表 vs 按需求镜头（M2，阻塞）

> 本节替代了原"5 话题抽象（M2）"与"3 判断信号抽象（M3）"两条独立阻塞项 —— 经第二轮考察确认这两条都是同一上游问题（scope 切分维度错位）的症状。"加具体例"作为 fix 是 stopgap，未触及根因。

**问题。** 当前共性画像的"典型职位"列了 5 个：创始人/CEO、COO、数字化负责人、业务线总经理、产品/技术负责人。这 5 个角色在信息消费、决策权、关注的时间尺度、专业语言上是**结构性分裂**的：

- CEO 看战略叙事与中长期赌局
- COO 关注当前季度的运营效率与组织调整
- 数字化负责人关注 IT / 平台落地的可行性与风险
- 业务线总经理关注业务结果归因与本线 P&L
- 产品 / 技术负责人关注技术栈与实施细节

**推论。** 把这些分裂的角色混在同一个"共性画像"里抽象出 5 话题 / 3 痛点 / 3 判断信号，**必然只能写到 benefit / concern statement 那种"看似都对但谁也对照不上"的层级**——最大公约数会向"所有 ToB 决策者都关心的事"收敛，A 层独有特征反而被磨平。

具体可观察到的两个症状：
- 共性画像 5 话题（"AI 能否在 90 天内提升核心业务效率"、"如何把 AI 从工具试用推进到组织流程"等）都是 benefit/concern statement，写手无法判断这是 1 篇文章还是 30 篇
- 共性画像 3 判断信号（"是否有可执行步骤"、"是否给出可衡量指标"等）停在抽象总纲，A1 / A2 样本却能轻易写到 "是否给出 4–8 周可观察到的结果" 这种 checklist 级具体度

**根因。** 共性是**需求镜头投影出来的产物，不是职位的并集**。"共性画像抽象、样本具体"的两级落差，根因不是抽象层故意写得高，而是共性画像的切分维度本身就错了——按职位列表汇总，几乎不可能不抽象。

**对"加具体例"修正。** 加具体表达例是 stopgap：v0.1 仓促合并时可救场，但若想 T2 / T3 / T4 真的省力，必须先把切分维度改对。否则 T2 partner 同样会面对一个跨多种合作模式的"共性画像"，再被迫加例子救场——同样的问题会在每一份 persona 重复出现。

**建议。** 共性画像的切分维度从"职位列表"切换到"需求镜头"。示意（具体切多少片由 mentor 拍板）：

- 切片 1：**评估 AI 能否带来真实 ROI 的人**（跨 CEO / COO / 数字化负责人）—— 该镜头下 5 话题 / 3 痛点 / 3 判断信号是真共性
- 切片 2：**评估技术栈与系统选型的人**（跨 数字化负责人 / 产品 / 技术负责人）—— 一套不同的 5 话题 / 3 痛点 / 3 判断信号
- 切片 3：**评估"组织和岗位会如何被重塑"的人**（跨 CEO / COO / 业务线总经理）—— 又一套不同的

**只要切片定义清楚，每个切片下的 5 话题 / 3 信号自然能写到具体度**——当前看到的"抽象度过高"是切分维度逼出来的伪问题，无需在抽象层硬塞例子。

**与 §2.3（M3）的协同。** §2.3 提出的 IC / DRI / PC 角色标签是"需求镜头"的一种具体可操作实现路径——这三类角色本身就是三种天然的需求镜头。M2 是结构层重构（决定 scope 怎么切），M3 是标注层增强（让每条事实显式归属一个角色镜头）；前者治本，后者帮前者落地。

### 2.3 IC / DRI / PC 角色标注缺失（M3，阻塞）

**背景。** 我们的目标受众（A 层"会推动 AI-native 落地的人"）所在的组织正在向 **IC / DRI / Player-Coach** 三角色重构（参见 Sequoia 2026-03-31 *From Hierarchy to Intelligence*，Block 在该模型下推进）。这三类角色对内容的吸收方式截然不同：

- **IC（Individual Contributor）**：深耕某层能力（capability / world model / intelligence layer / interface）的 specialist；关心技术实施细节、平台稳定性、specialist craft 的进展。读到"工具碎片化"会立刻代入"我这一层下的依赖管理与接口约束"。
- **DRI（Directly Responsible Individual）**：拥有 90 天跨切面客户问题（例如"merchant churn"）的责任人，可从模型层 / 能力层 / 接口层调度资源做出客户产出。读到"AI 项目停留在 demo"会立刻代入"我这次 90 天目标怎么别被这种事卡住"。
- **PC（Player-Coach）**：合并建设 + 育人的角色，替代传统中层管理；不主持 status / alignment 会议，主要投入在 craft 传承 + 团队成长。读到"多团队协同成本高"会立刻代入"我团队跨域协作的辅导成本"。

**问题。** persona-a-client.md 当前所有痛点 / 反对意见 / 话题 / 判断信号都是不分角色的混合表述。写手做选题时无法判断："这条信号是写给客户方的 DRI 看的，还是给 PC 看的，还是给 IC 看的？"——三类人即便都在同一家 A 层客户公司，对内容的接受方式完全不同。

**示范已存在于本评审 §3.2。** 在工具碎片化 / shadow IT 痛点条目上分别标了 (DRI) / (PC) / (IC)，可作为持久标注的样板。

**建议。** persona-a-client.md（以及 T2/T3/T4）应当对每条**痛点 / 反对意见 / 话题 / 判断信号**附加 IC / DRI / PC 角色标签：

- 标签放在条目末尾括号里，例如：「AI 项目停留在 demo，无法进入稳定生产流程（DRI）」
- 一条可多标，例如：「多团队协同成本高（DRI, PC）」
- 共性画像层 + A1 / A2 / A3 样本层 都需标注
- 同一条事实在不同切片（参见 M2）下对不同角色的标签可能不同——这是预期行为，不视为不一致

**理由（为什么阻塞）。** 不带角色标签的 persona，T2/T3/T4 复用时同样不会标。T1 阶段不立此标尺，后续要补就要四份一起回填，成本翻 4 倍；且没有角色标签时，写手做选题时只能凭感觉判断"这条对谁说"，与 task-02 交付目标"写手对照标题"的具体度要求相悖。

## 三、内容质量评估

### 3.1 已经写得好的部分（可作 T2/T3 模板）

- A2 的反对意见第 2 条："外部案例很漂亮，但我们的业务复杂度更高。"——主目标群体真实会有的反弹，写手看到这条就知道开篇要先承接"我和你不一样"的预设。
- A2 的判断信号第 2 条："是否有失败模式与回退方案"——比较尖锐的问题，最好能明确什么是A2所谓的失败模式。
- "对选题的直接启发"小节存在的事实本身——任务清单未要求该节，但这是把 persona 与栏目直接连起来的桥。这个 pattern 强烈建议保留并在 T2/T3 复用。

### 3.2 痛点覆盖面（S2，建议改）

当前 3 条：
1. AI 项目停留在 demo
2. 多团队协同成本高
3. 难以量化 AI 价值

**问题。** 1 与 3 实质都是"投入-产出失衡"，重叠度较高。缺少两类常见痛点：
- "已经有一批 AI 工具，但形成不了组合拳"（**工具碎片化 / shadow IT**）——50–2000 人中段企业极常见，可直接映射到栏目「协作拓扑」（DRI）
- "VP 们各自买 AI 工具，IT/数字化部门管理不过来"（PC）

**建议。** 替换或补一条工具碎片化类痛点（IC），1 与 3 二选一保留。

### 3.3 反对意见力度不足（S3，建议改）

当前 2 条：
1. ROI 不稳定，浪费预算
2. 没有人才维护，不可持续

**问题。** 两条均为"安全保守型"反对，写手用一段开头（"我们给你 ROI 数据 / 我们给你 maintenance-light 方案"）就能化解。反对意见的价值在于"写作时知道要先化解什么质疑"——目前两条对写手的约束力太弱。

**更尖锐的候选（任选其一替换或新增）：**
- "数据 / IP 泄露：我们的核心知识喂给了别人的模型"
- "供应商锁定：选了某家 agent 平台后切换成本太高"
- "内部政治阻力：业务线不愿被数字化部门统一标准"

**建议。** 至少替换 1 条到上述更尖锐类型。

### 3.4 样本多样性缺一类高匹配度受众（S1，建议补）

当前覆盖：
- A1：中型 ToB SaaS COO（300 人）
- A2：区域连锁服务数字化负责人（800 人）

**问题。** mentor 主目标原话是"吸引认同 AI-native 组织理念的客户"。**最高匹配度的群体——新近融资的 AI-native 创业公司本身——反而没有出现在样本里。** 这类受众：
- 创始团队本身在做 AI 产品
- 极愿意为"AI-native 组织怎么搭"付费 / 合作
- 信息源是 X / Hacker News / 公众号 + 小红书的混合，与 A1/A2 截然不同
- 不会出现"没人才维护"反对，但会出现"我们自己就是 AI 公司，你能给我什么我不知道的"

**建议。** 增加 A3 样本覆盖此类，让 T2/T3 在多样性轴上有参照。

### 3.5 「对选题的直接启发」颗粒度可再下沉（S4，建议改）

当前形式：
> 周观察类：优先写"组织级流程重写"和"AI KPI 量化"
> DRI 拆题类：优先写"低预算试点 + 风险兜底 + 回退方案"
> 5 signal 类：优先收集"企业级部署、治理、ROI 与岗位变化"信号

**问题。** 写手 / 选题会拿到这一节，离"今晚就开干"还差一步——还需要把方向再拆成具体选题。

**建议。** 改成 **A 层 5 话题 × 3 栏目 = 15 格的候选选题表**，每格至少 1 条具体选题。即使留白几格也比留抽象方向更有价值。

## 四、与 init-plan 的对齐分析

### 4.1 受众分类的演化

| 来源 | 受众分层 |
| --- | --- |
| init-plan §1.3 | C 端（潜在员工/追随者）vs B 端（客户/合作方/生态建设者）—— 二分 |
| task-02 | A 客户 / B 合作方 / C 潜在员工 / D 行业观察者 —— 四分 |

**观察。** task-02 把 init-plan 的 B 端拆成 A（客户）+ B（合作方），把 C 端进一步分出 C（潜在员工）+ D（观察者）。**persona-a-client = 新 A 层 = 旧 B 端的客户子集。** 拆分方向合理，但需要在 T6 核心信息或 T7 glossary 里明示这个映射，否则后续提到"B"会指代不清（旧 init-plan B 端 vs 新 task-02 B 合作方）。

### 4.2 渠道层冲突点（已声明的修订未在文档留痕）

| 来源 | A 层（核心客户）的主阵地 |
| --- | --- |
| init-plan §1.3 | B 端 → 微信公众号、Medium、Reddit |
| task-02 mentor 拍板 | 公众号 + 小红书 + 抖音 |
| persona-a「日常阅读 3 个平台」 | 公众号 + 小红书 + 抖音 |

**观察。** mentor 拍板时**去掉了 Medium / Reddit，加上了小红书 / 抖音**。后两者在 init-plan 里属于 C 端通道。

**修订的合理性：**
- 公众号保留：B 端长内容主阵地不变
- 加小红书 / 抖音：考虑到中国 ToB 决策者实际"刷手机"行为，及"案例切片 / 趋势速览"的认知入口
- 去掉 Medium / Reddit：阶段一聚焦中文区，海外阵地后置

**问题。** 这次渠道修订**没有任何文档注释**留痕。persona-a 直接采用了修订后的版本，但读者从 init-plan 读到 persona-a 时会不明白为何渠道清单变了。这种隐式修订也是 §2.1 M1 字段语义模糊的根源——"渠道战略"被装进了"用户画像"字段。

**建议。** 在 init-plan §1.3 或 task-02 顶部加 1 段版本演进注释，明示"主阵地 = 公众号 + 小红书 + 抖音；Medium / Reddit 阶段一不做"。属于 §七 回流建议。

### 4.3 内容矩阵 × A 层话题映射

init-plan §2 内容矩阵把选题维度分成 4 列（当前热点 / 底层技术突破 / 深度竞品分析 / AI 哲学），且 B 端在"深度竞品分析"和"AI 哲学"两列**留空**。

把 persona-a 的 5 个话题映射回去：

| persona-a 话题 | 对应 init-plan 选题维度 |
| --- | --- |
| 1. 90 天内提升核心业务效率 | 当前热点 + 案例 |
| 2. AI 从工具试用进入组织流程 | 当前热点 + 内部 SOP |
| 3. 人机协同后的岗位与管理 | **AI 哲学**（init-plan B 端原本留空） |
| 4. 成本、合规、治理风险 | AI 哲学 / 治理（init-plan B 端原本留空） |
| 5. 与竞品的落地速度与产出差异 | **深度竞品分析**（init-plan B 端原本留空） |
| —— | 底层技术突破（A 层不出现，合理） |

**观察：**
- persona-a 实际**比 init-plan B 端覆盖更广**（填上了原本留空的两列）—— 这是 task-02 收紧目标后的合理扩展。
- "底层技术突破"在 A 层完全不出现 —— 合理（A 层是"会推动落地的人"，不是研究 MCP 协议细节的人）。但应**显式声明 A 层不读底层技术内容**，避免后续选题会把这类内容硬塞给 A 层。

## 六、给 T2 / T3 / T4 的字段约定（T1 锁定后通用）

T1 初审最大的杠杆点是**为后 3 份 persona 立标尺**。以下约定建议在 T1 修订并合并后写入 task-02 顶部，作为 T2/T3/T4 共同遵守的字段规范。前两条来自本次评审的 M2 / M3，是结构性原则，优先级最高。

1. **Persona scope 必须以"需求镜头"为切分维度**（M2 立的标）：scope 不是职位列表的并集，而是一个清晰的"看待 AI 的视角"或"需要解决的问题类型"。每份 persona 文档应在顶部用 1–2 句话定义自己的需求镜头；若该层有多镜头需求，则切多个切片，每片独立写 5 话题 / 3 痛点 / 3 判断信号。**禁止把跨需求镜头的多角色合并成一个共性画像然后被迫抽象。**
2. **IC / DRI / PC 角色标签贯穿条目**（M3 立的标）：每条痛点 / 反对意见 / 话题 / 判断信号末尾用括号标注（IC / DRI / PC），三类同时关注则用（IC, DRI）等组合。共性画像层与样本层都需标注。同一条事实在不同需求镜头切片下可有不同标签，不视为不一致。
3. **「日常阅读的 3 个平台」语义统一**：四份 persona 必须使用同一种语义（真实行为 OR 我方主阵地），由 T1 修订时拍板。
4. **「最关注 N 个话题」具体度**：每条不能停在 benefit statement，必须给到用户在搜索框 / 讨论里出现的具体表达级别。在 #1 切分维度改对后此具体度自然达到；切分维度未改前不允许靠"加例子"伪装达到。
5. **「判断信号」具体度**：写手能当 checklist 用。同 #4，依赖 #1 切分维度改对。
6. **典型职位跨度**：作为切片**结果**列出，不作为切片**起点**。共性画像不再先列职位再抽象出共性。
7. **典型组织规模区间**：要么收窄，要么用样本覆盖区间两端。
8. **样本数量与多样性**：≥ 2 个，需覆盖该层的核心多样性轴（A 层 = 行业类型 × 组织阶段；T2 partner 建议锁定 = 合作模式 × 共建深度；T3 talent 建议锁定 = 技术栈 × 资历段）。
9. **「对选题的直接启发」小节保留**：T1 自创的这一节是 persona → 栏目的关键桥梁，T2/T3/T4 必须有对应章节，颗粒度建议直接做成"话题 × 栏目"候选选题表。
10. **可选字段**：决策周期 / 典型一周日程片段 / 最近三个月真实关注的事件——强烈建议但不强制。
11. **字段语义注释**：每份 persona 顶部加 1–2 行字段语义说明，避免歧义传递。
